# Unity.Rea.Chain: Project Bible

> The single source of truth for what Unity.Rea.Chain is, the rules that keep the rebuild faithful, how the code is
> organised, and every place it does not play exactly like the original, with the reason. `README.md` says how to
> build and run it; [`RECONSTRUCTION.md`](RECONSTRUCTION.md) is the full reverse engineering of the original and
> the build order to parity; [`chain-physics.md`](chain-physics.md) is the spring algorithm and its tuning.
>
> Every behaviour of the original is on main, fixed or recorded here (U.CHN-T63, [RECONSTRUCTION §8](RECONSTRUCTION.md));
> V4 and V12 are settled (U.CHN-T76). Nothing is claimed as built that is not.

## 1. The one sentence {#UNI-§1}

A mouse-steered angel flies an endless arena swinging a spiked mace on a spring chain, knocking down, grappling
and throwing a flock of enemies that home in on it, rebuilt from the 2005 VB.NET / DirectX 9 *Chain Game* (itself a
port of Philip Winston's 2000 *Elastic Trail* script) as a modern Unity 6 game.

## 2. The product promise {#UNI-§2}

- **The chain is the game.** Every link is a Hookean spring with drag and gravity, so the mace lags, swings and
  whips; circling the mouse winds it up like a flail, and the overhead boost keeps it from drooping when swung high.
- **Hit, grab, throw.** A mace hit knocks an enemy back by the mace's velocity over its mass and scores the damage
  x 1000. Hold the button and the mace grabs instead; release and the enemy flies off at the mace's velocity,
  bowling over any enemy it touches.
- **One arena, one loop.** 14 enemies seek the angel, 30 HP drains one touch at a time, one heart drifts down for
  +10, and at zero the light fades and the round resets itself.
- **Every knob of the original.** The `[` `]` chain length, the live spring, drag and gravity keys, gem link skins,
  backgrounds, lighting, screen shake, debug views and the script console all come across (all on main, see
  [RECONSTRUCTION §6](RECONSTRUCTION.md)).

## 3. What it is not {#UNI-§3}

- **Not a redesign.** No new modes, levels, enemies or progression. The scope is the original, played as it was
  meant to play (see [§4 rule 1](#UNI-LAW-1)), and the repo is finished when the last reconstruction story is.
- **Not a line-by-line port.** The code is rebuilt from scratch to current Unity practice; only the behaviour is
  kept.
- **Not frame-rate dependent.** The original's per-frame numbers are converted to a fixed step.

## 4. Design rules {#UNI-§4}

The owner's rebuild standard is in [`AGENTS.md`](../AGENTS.md); these are its rules as they apply here.

### {#UNI-LAW-1} Gameplay matches the original; broken things are fixed

Every value, unit and behaviour comes from the original source (`R:\...\Chain Game\`), never from a guess. Where the
original is plainly broken (a random that is not random, a draw call commented out, a feature that can never be
reached, sound that ships switched off) the rebuild plays the way the game was clearly meant to, and the fix is a
row in [§7 Fixed defects](#UNI-§7). Everything that works matches exactly. Anything else that differs is a row in
[§8 Deliberate deviations](#UNI-§8) with its reason. A difference with no row is a bug.

### {#UNI-LAW-2} Reverse-engineer before rebuilding

A module is read in full and recorded in `RECONSTRUCTION.md` before its rebuild starts.

### {#UNI-LAW-3} Core is pure C#

The rules live in an engine-free Core assembly (
oEngineReferences`, no `UnityEngine`) tested with `dotnet test`.
State changes only through commands, which produce events; presentation reads state and plays events and never
mutates the game.

### {#UNI-LAW-4} Hard assembly boundaries

Core, Runtime, Editor and Tests are separate asmdefs with one-way references (see [§5](#UNI-§5)).

### {#UNI-LAW-5} Content and tuning are data

Every tuning number lives in a data file or the settings registry and is validated on load (see [§6](#UNI-§6)).

### {#UNI-LAW-6} Built in code

The scene, UI and objects are composed in code (`SceneBuilder`, `PlayerBuilder`), never wired by hand in the
Inspector. Regenerate `Main.unity` rather than editing it.

### {#UNI-LAW-7} Modern Unity only

Unity 6, URP behind a pipeline-agnostic layer, the Input System through an action asset, UI Toolkit or the shared
MindAttic components, Unity.Shared profiles and settings, and multiplayer-ready seams: commands carry a player id,
one authority holds the state, no global current-player singleton, built on the Unity.Multiplayer kit.

### {#UNI-LAW-8} Done means seen working

Core tests green, a build that launches, and the feature seen in play (a screenshot or a scripted run) before a
ticket closes.

### 5.3 Commands, events and the one authority

The whole game is one `GameWorld` (Core): the session rules (`GameState`), every seated player (`PlayerEntity`:
their `AngelFlight`, `ChainSimulation`, mace link and `Grapple`) and every enemy (`EnemyEntity`: an id, its
`EnemyBrain`, its position and radius). One authority holds it, `GameSession`, and nothing else changes it:

- **Commands in.** A player's input becomes a `GameCommand` carrying that player's `PlayerId`: `SteerAngel` (mouse
  delta, applied on arrival so steering is as smooth as the display), `ArmGrapple`, `ReleaseGrapple`,
  `ChangeChainLength`, `ToggleFollow` (the F key), `SkinLinks` (the U key), `ToggleMaceMode` (the M debug key), `TuneChain` (the live-tuning keys), `ChangeGameSpeed` (Minus/Equals, held), `Pause`, `TogglePause`, `ResetGame`. `GameSession.Submit` hands it to `GameWorld.Submit`.
  Commands are plain immutable data, so a networked player's NetEntity can carry them to the authority unchanged.
- **One step.** `GameSession.FixedUpdate` is the only caller of `GameWorld.Step`: chains swing from their angels'
  hands, enemies seek the nearest angel, flock and (thrown) knock each other, grapples arm, catch, carry and throw,
  each mace hits what its swept circle touched, enemies touching an angel cost HP, and a finished game fades and
  resets itself. Every step runs at the world's `GameSpeed` (V20): it plays that many fixed steps' worth of game
  time, in sub-steps no longer than one fixed step (`TimeScale`). Contacts are circle tests in Core (`Sweep`, `EnemyEntity.Overlaps`), not Physics2D queries, so all
  of it runs and is tested under `dotnet test`. The world holds the hearts too (`GameWorld.AddHeart`, a
  `HeartFloat` each): it moves them, checks them against the angels (`CheckHearts`, `CollectHeart`) and resets
  them; `HeartPickup` only draws one.
- **Events out.** Everything that happens is a `GameEvent`, in order: `EnemySpawned`, `EnemyRemoved`, `EnemyHit`,
  `EnemyKnocked`, `EnemyKilled`, `GrappleChanged`, `Grabbed`, `Thrown`, `ChainLengthChanged`, `FollowChanged`, `LinksSkinned`, `MaceModeChanged`, `ChainTuned`, `GameSpeedChanged`, `AngelHurt`,
  `AngelHealed`, `PauseChanged`, `GameOver`, `WorldReset`. `GameSession.EventRaised` passes them on after each
  command and step; `EnemySpawner` makes and kills enemy views from them, `ChainAudio` plays its player's hits,
  catches and throws, and the session freezes time on `PauseChanged`.
- **No current player.** Each seat is a `PlayerId`; `GameSession.Join` seats an angel and its chain, and each of
  those components holds its own id. Nothing looks up "the" player. Two seats already play side by side in the
  world (each with its own angel, chain and grapple; a hit is credited to the mace that landed it).
- **Tuning** is data (§6): the authority seats each player from the settings registry (`GameSession.Settings`,
  loaded from `StreamingAssets/Settings`), and a component can only override a figure at run time (live tuning,
  tests), which goes to the world through `GameSession.Retune`.

While paused the camera shows only the backdrop's layer (`AreaBackdrop.Layer`, "Backdrop"): `oneFrameRender` draws
only `renderCube`, `renderBackground` and the banner then, so the play field disappears until the game resumes
(`CameraRig.ApplyPauseView`, U.CHN-T78).

Where the world departs from the earlier component wiring: pausing now freezes the angel too (Engine.vb renders and
moves the angel only while not paused; the port had kept flying it), and a finished game resets the world in place
instead of reloading the scene (V15).

### 5.4 Online: the Unity.Multiplayer kit (U.CHN-T26)

The game is built on the shared kit (Unity.Multiplayer, MindAttic Components for its menus, Unity.Shared for the
player's name and colour; `Packages/manifest.json`, NGO under `testables`, `MINDATTIC_NGO_TESTABLE` committed in
`ProjectSettings.asset`). Its one rule is the game's own (§5.3): one authority holds the state, players send what they
want to happen.

- **Local play is unchanged.** Main opens straight into play as before; the NetworkManager's `NetBootstrap` never
  starts a session by itself (`autoStart` off, `serveWhenHeadless` off, so batch-mode runs play locally), the kit's
  menus stay hidden, `GameSession` applies its own commands and Escape quits (V8).
- **The front end beside it.** O (V26) opens the kit's `NetFrontEnd`: Host, Join by IP, Join by code, Settings (the
  player's name and colour), Play alone (back to local play) and Quit. Host shows the lobby with the join code (or the
  LAN address when no code service is set up) and the roster; Start begins. While a session runs, Escape opens the
  kit's in-game menu (Resume, Invite, Settings, Leave or End game) instead of quitting (`GameSession.HoldsQuit`). While
  a menu is open the game's input is held back (`InputGate.SetMenuOpen`), the cursor is free, and on the main menu
  outside a session the local game is paused, as behind the config screen (V21).
- **Players carry their seat.** Every connection gets a `ChainPlayer` (NetEntity, the Player Prefab). The server gives
  it the connection's seat from the roster (`[Synced] Seat`, stable across a reconnect), and the seat is its
  `PlayerId`: the host's own seat is the scene's angel; any other seat the authority adds to its world
  (`GameSession.AddRemotePlayer`, tuned as its own angel) and takes out when the player is gone
  (`RemoveRemotePlayer`). A dedicated server (`-mode server`) seats its first player on the scene's angel.
- **Commands into the server.** On a client, `ChainPlayer` sets its screen's `GameSession.Forward`: every command the
  input readers make (the same `SeatInput`, `AngelController`, grapple, mace and HUD code as local play) goes to the
  server as `CommandCodec` bytes (`[ToServer] Send`) instead of changing the client's world, which is no longer
  stepped. The server decodes them as the sender's seat, whatever id the bytes name, refuses anything malformed, and
  submits them to its `GameSession`. `QuitGame` is never sent.
- **State back for presentation.** The server writes each seat's angel and mace to `ChainPlayer` (`[Synced]`), drawn
  as a marker in the player's roster colour where the peer has no angel of its own for that seat, and
  `ChainWorldSync` (spawned by key, `chain:world`, when a server's session starts) sends the whole world 20 times a
  second as a Core `WorldSnapshot` (HP, score, pause, game over, every seat's angel, chain and mace, the enemies and
  the hearts, plus the round clock and each enemy's radius since wire version 2), which every peer keeps as `Latest`.
- **A client draws the authority's game (U.CHN-T73).** Every frame the owning client's `ChainPlayer` hands `Latest` to
  its screen's `GameSession.ShowAuthority` with its seat (`Shown`, `ShownSeat`; dropped the moment the screen stops
  forwarding). The views then read it in place of the frozen local world: the angel, chain and mace draw that seat's
  entry (position, facing, flap frame, the links hand to mace, the mace link, skin and armed grapple), the
  `EnemySpawner` keeps one view per snapshot enemy and hides the local flock, each heart draws the authority's heart at
  its own place in the world's list, and the HUD, the light and the camera show its HP, score, clock, game speed, pause,
  game over and fade. Every other seat is drawn by its `ChainPlayer` marker: the angel sprite in the roster colour with
  its chain line and mace (from the authority's world on the host, from `Latest` on a client). Not carried, so not
  drawn from the snapshot: the gem link skins (hidden over the shown chain), the live-tuning readout and the grappled
  enemy's HP (both the screen's own), and the sounds (played from local events). Snapshots are drawn as they arrive,
  20 a second, with no interpolation between them.
- **Bots and tests.** `ChainBot` is the game's `[NetBotDriver]` (`-bot A`): it waits for its seat, steers and swings
  with the same commands, and passes once the authority has moved its angel. `Tests/Online` runs on the kit's
  `NetSessionTest` (a host and a client: seats, forwarding as the sender's seat, refused bytes, snapshots, leaving) and
  `NetBotTest` (a dedicated server and two bots joining by code). The wire formats are `dotnet test`ed
  (`NetWireTests`).

## 6. Data files {#UNI-§6}

**The original had none.** Its Jet `.mdb` databases are commented out and `loadTerrain` reads an unset `DataRow`;
every number is a field in code. The only persisted data is the registry (`HKCU\Software\MindAttic\Engine` read,
`...\War` written) with Width, Height, ColorDepth and Fullscreen.

**The rebuild** (UNI-T33) keeps every tuning figure in JSON files in `Assets/StreamingAssets/Settings/`, one per
concern, read by Core's settings registry (`Core/Settings/GameSettings`) through an interface (`ISettingsSource`;
the build reads the folder with `DirectorySettingsSource`, Runtime's `SettingsStore` holds the loaded registry).
Nothing tunes the game from the Inspector any more.

- **The files hold the original's figures in its own units**, named as its source names them (`segLength`,
  `springK`, `Ratio3D`, `seekSpd`, `floatSPD`, ...): screen space, where -0.5..0.5 is the screen height, and per
  frame. A figure the original never had (a circle radius where it tested rectangles, the camera rig, the swing
  whoosh) sits in that file's `port` object, in world units and seconds, and is never mapped. Keys starting with
  `_` are notes.
- **One mapping** turns them into the port's: `space.json` (`lengthScale`, `framesPerSecond`) read into
  `OriginalSpace`, which `GameSettings.Map` applies to each figure by kind (length, speed, acceleration, rate,
  frames). It is the only place a figure changes units. `lengthScale` is 9 (UNI-T66): the original's screen height
  (1.0) is the 9 world-unit height of the 16 x 9 arena, so every position, size, speed and acceleration is the
  same fraction of the screen as in the original. The original ran 4:3 (Camera.vb, 640 x 480); x uses the same
  scale, so the wider arena is simply more room at the sides. Port-only figures (radii, hand offset) were
  re-checked against the scaled rectangles: hit 0.3, catch 0.35, enemy 0.3, angel contact 0.4, hand (0.3, 0).
- **Validated on load**: every key must be present, of its type and in range, unknown keys are reported (a typo is
  not silently ignored), and cross-checks hold (`Mace` within `maceMin..maceMax`, `seekCap` no more than the
  enemies, `hangBackFar` beyond `hangBackNear`). One load reports every problem, each with its file, key and line (`SettingsException`); the game logs
  them and does not start on bad data. `Tests/Core.Tests/GameSettingsTests` loads the shipped files.

resolution, music and sound-effect volumes into the profile and Chain's own `game.ambientVolume` (the shared block has no

## 10. Glossary {#UNI-§10}

- **Link**: one point of the chain; link 0 is pinned to the angel's hand.
- **Mace**: the heavy end link at index `Mace` (1..12, default 6), drawn 3.5x.
- **Grapple**: holding the button turns a mace hit into a grab; release throws.
- **Hurt**: an enemy's knocked-back state; it decelerates, then seeks again.
- **Thrown**: a Hurt enemy launched by the grapple; it knocks over the enemies it touches.
- **Reset**: the original's full round restart (score, timer, light, angel, enemies, heart, music).
- **The original**: the VB.NET / DirectX 9 Chain Game at `R:\...\Chain Game\`.
